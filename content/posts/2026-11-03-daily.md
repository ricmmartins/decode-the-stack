### [Building a browser GIF editor: the frame memory limit matters more than file size](https://dev.to/_3330b5103afff1/building-a-browser-gif-editor-the-frame-memory-limit-matters-more-than-file-size-45k9)
*Decoded workload, rather than compressed upload size, determines the editor’s most important resource boundary.*

The developer of VisualFormat describes a mismatch between file size and processing cost. A 1,000-by-1,000-pixel animation with 100 frames represents 100 million frame pixels; retaining every frame as RGBA data would require roughly 400 MB before working canvases and encoding buffers. A small download therefore says little about whether a browser can comfortably edit the animation.

VisualFormat scans GIF blocks before allocating decoded frames, checking dimensions, frame count, and total canvas pixels across the animation. Its stated limits are 20 MB, 500 frames, 4,096 pixels per dimension, and 40 million total frame pixels. This approach validates the expanded workload before committing resources. The author describes these limits as guardrails, not a promise that every accepted file will work on every device.
